Spring Cloud AWS — SQS ack batch entry-id 중복 (GH-1634)

Standard SQS 큐가 ack 배치가 flush 되기 전에 같은 메시지를 재배달하면 SqsAcknowledgementExecutor가 Spring message id (SQS messageId에서 파생) 를 DeleteMessageBatchRequestEntry.id로 그대로 써서 같은 배치에 중복 entry id 두 개가 실렸습니다. AWS 는 배치 전체를 BatchEntryIdsNotDistinctException 로 거절. positional-index id 로 교체해 요청 로컬 유니크성만 보장하도록 좁혔습니다.

문제 — GH-1634

Standard SQS 는 at-least-once 재배달을 정상 동작으로 허용. 하나의 ack 배치가 flush 되는 짧은 창 안에서 같은 message 가 두 번 도착하면 SqsAcknowledgementExecutor가 두 항목 모두를 DeleteMessageBatchRequestEntry 로 변환하며 MessageHeaderUtils.getId(msg) — SQS messageId 기반 — 을 .id()로 세팅. 같은 배치 안에 같은 id 두 개가 실려 AWS 가 배치 전체를 BatchEntryIdsNotDistinctException 로 거절. ack 실패로 이어져 visibility timeout 뒤 같은 메시지가 또 재배달되는 악순환.

수정 — positional-index id

Batch entry id 는 요청 로컬 correlation token 일 뿐이라 요청 스코프의 유니크성만 있으면 충분합니다. Spring message id 대신 Integer.toString(index) 를 entry id 로 사용:

  • SqsAcknowledgementExecutor.createBatchEntries: IntStream.range 로 인덱스를 붙여 DeleteMessageBatchRequestEntry.id 에 positional id 세팅. Spring message id 는 로그/correlation 용도로만 유지.
  • Partial-failure 매핑: AWS 응답의 실패 id 를 index 로 parse 해 원본 메시지로 역추적. Parse 실패 시 기존 "cannot correlate all failure ids" fallback 경로로 흡수 — 파괴적 변화 없음.

회귀 테스트

SqsAcknowledgementExecutorTests 에 케이스 추가. 같은 SQS message id 를 가진 두 Message 를 하나의 배치에 넣고 DeleteMessageBatchRequest 로 캡처, entry id 두 개가 서로 다른지 확인. 추가로 partial-failure 응답에서 실패 index 가 원본 메시지로 정확히 매핑되는지, 그리고 parse 안 되는 id 가 반환됐을 때 fallback 경로가 트리거되는지도 검증.
